# 작업 방식: 명세 주도 개발 (SDD + BDD)

> 출처: Jaroslaw Wasowski, ["SDD Writing Specifications for AI: BDD as the Missing Link"](https://levelup.gitconnected.com/sdd-writing-specifications-for-ai-bdd-as-the-missing-link-spec-driven-development-ad1b540b7f75), Level Up Coding, 2026-04-28
>
> 원문은 Medium 유료 글이라 공개된 서론의 핵심 주장(아래 1장)만 확인했습니다. 2장부터는 그 주장을 이 프로젝트에 적용한 규칙입니다. 원문을 읽고 다른 점이 있으면 이 문서를 고칩니다.

## 1. 핵심 주장

1. **AI가 코드를 쓰는 시대에 명세는 보관용 문서가 아니라 실행 계약이다.** AI는 사람 동료처럼 모호함을 알아서 메워주지 않는다.
2. **중요한 질문은 "명세가 필요한가"가 아니라 "명세에 무엇을 담는가"다.**
3. **Given/When/Then 시나리오 하나가 비즈니스 명세이면서 동시에 단위, 통합, E2E, 인수, 회귀 테스트다.** BDD가 사람의 의도와 AI의 구현을 잇는 빠진 고리다.

## 2. 이 프로젝트의 명세 계층

위에서 아래로 갈수록 구체적이고, **위가 아래를 이깁니다.** 서로 어긋나면 위 문서를 기준으로 아래를 고칩니다.

| 순서 | 문서 | 담는 것 | 답하는 질문 |
|---|---|---|---|
| 1 | [PRD.md](PRD.md) | 문제, 사용자, 범위, 단계 | 왜, 무엇을 |
| 2 | [open-questions.md](open-questions.md) | 결정 사항과 미결 항목 | 무엇을 정했나 |
| 3 | [permissions.md](permissions.md) | 역할과 권한 | 누가 할 수 있나 |
| 4 | [glossary.md](glossary.md) | 용어, 값, 화면 이름, **표준 문장 카탈로그** | 어떤 말로 쓰나 |
| 5 | [../features/](../features/) | Given/When/Then 시나리오 | 정확히 어떻게 동작하나 (**실행 계약**) |
| 6 | [erd.md](erd.md) | 테이블, 제약, 설계 결정 | 데이터를 어떻게 담나 |
| 7 | 코드와 Step Definition | 구현 | 계약을 지키는가 |

## 3. 기능을 바꿀 때의 순서

**코드부터 고치지 않습니다.** 항상 이 순서를 따릅니다.

1. **결정**: 무엇을 바꾸는지 정하고 [open-questions.md](open-questions.md)에 기록한다. 사람이 정할 일이면 묻는다.
2. **PRD / 권한**: 범위나 권한이 바뀌면 [PRD.md](PRD.md), [permissions.md](permissions.md)를 고친다.
3. **용어**: 새 용어, 상태, 화면, 문장이 필요하면 [glossary.md](glossary.md)에 먼저 추가한다.
4. **시나리오**: `features/*.feature`를 고치거나 추가한다.
5. **검사**: `python3 scripts/check_steps.py`가 통과해야 한다.
6. **데이터**: 필요하면 [erd.md](erd.md)를 고친다.
7. **구현**: 4번의 시나리오를 통과시키는 코드를 쓴다 (4장).

## 4. 구현 루프 (시나리오 하나씩)

1. 구현할 시나리오 **하나**를 고른다. Phase 순서와 [glossary.md](glossary.md) 카탈로그 사용 횟수가 많은 문장부터 고르면 효율적이다.
2. 그 시나리오의 Step Definition을 작성하고 실행해서 **실패를 확인한다** (RED).
3. 시나리오를 통과시키는 **최소한의 코드**를 쓴다 (GREEN).
4. 중복을 정리한다 (REFACTOR). 다른 시나리오가 깨지지 않았는지 전체를 다시 돌린다.
5. 다음 시나리오로 간다.

시나리오에 없는 동작은 만들지 않습니다. 필요하다고 판단되면 3장의 순서로 시나리오부터 추가합니다.

## 5. 시나리오 하나 = 여러 계층의 테스트

같은 시나리오를 여러 계층에서 실행할 수 있도록 Step Definition을 나눕니다(뼈대를 만들 때 확정).

| 계층 | Step Definition이 하는 일 | 예정 태그 |
|---|---|---|
| 도메인 / 서비스 | 서비스 메서드를 직접 호출 | `@service` |
| API (통합) | HTTP로 호출하고 DB 상태 확인 | `@api` |
| E2E | 브라우저로 화면을 조작 | `@e2e` |

- 시나리오 문장은 계층과 무관하게 **선언형**으로 쓴다. "버튼을 클릭한다"가 아니라 "할 일을 완료하면"으로 쓴다.
- 화면 이름(`"팀 할 일 목록"` 등)은 [glossary.md](glossary.md) 4장의 값이다. Step Definition이 계층에 맞게 API 조회나 화면 조회로 바꾼다.
- 모든 시나리오는 회귀 테스트로 CI에서 계속 돈다.

## 6. 테스트할 수 있게 만들기 위한 코드 규칙

- **시간**: `Clock`을 주입받는다. `LocalDateTime.now()`를 직접 부르지 않는다. 시나리오의 `오늘은`, `시각이 ~이 되면`, `서버가 ~부터 ~까지 꺼져 있었다`가 이 `Clock`을 움직인다.
- **무작위**: 룰렛은 `RandomGenerator`를 주입받는다. 테스트에서 고정값을 넣는다.
- **외부 호출**: 슬랙 발송은 인터페이스 뒤에 둔다. 테스트에서는 보낸 메시지를 기록하는 가짜 구현을 쓴다.
- **권한**: 서비스 계층에서 검사한다. 그래야 서비스 계층 테스트에서도 `접근 거부 응답을 받는다`를 확인할 수 있다.

## 7. 완료 기준

기능 하나가 끝났다고 말하려면:

- [ ] 관련 시나리오가 모두 통과한다
- [ ] 다른 시나리오가 깨지지 않았다
- [ ] `python3 scripts/check_steps.py`가 통과한다
- [ ] 명세에 없는 동작을 추가하지 않았다
- [ ] 바뀐 결정이 [open-questions.md](open-questions.md)에 기록되어 있다
