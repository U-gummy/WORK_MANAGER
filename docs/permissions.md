# 권한 설계 (초안 v0.5)

> v0.5 변경: 프로젝트, 고객사, 업무, 보고서 권한 추가.
> v0.3 변경: 단일 팀. 역할은 관리자(1명)와 팀원뿐. 슈퍼 관리자, 다중 팀, 팀 선택, 비공개 기능 제거.

## 1. 원칙

- 서비스 하나 = 팀 하나. 로그인한 모든 사용자는 같은 팀이다.
- **업무 데이터는 모두 팀 전체에 공개**된다.
- **수정과 삭제는 본인이 만든 것만** 할 수 있다. 관리자도 예외가 아니다.
- 관리자는 팀원이 하는 모든 일을 할 수 있고, 거기에 관리 기능이 더해진다.

## 2. 역할

| 역할 | 코드 | 인원 |
|---|---|---|
| 관리자 | `ADMIN` | 정확히 1명 |
| 팀원 | `MEMBER` | 제한 없음 |

### 관리자 1명 유지 규칙

- 첫 관리자는 최초 실행 시 환경변수로 만든다([features/bootstrap.feature](../features/bootstrap.feature)).
- 관리자는 **위임**으로만 바뀐다. 관리자가 활성 팀원 한 명을 골라 위임하면, 그 사람이 관리자가 되고 본인은 팀원이 된다. 한 트랜잭션에서 처리한다.
- 관리자 계정은 비활성화할 수 없다. 먼저 위임해야 한다.
- 관리자가 잠기거나 비밀번호를 잊으면, 서버 명령으로 초기화한다(관리자 위에 사람이 없으므로).

## 4. 계정 비활성화 정책

관리자가 팀원 계정을 비활성화하면:

1. 그 사람은 **로그인할 수 없다.** 로그인 중이었다면 다음 요청부터 거부된다.
2. 작성한 할 일, 이슈, 배포일정, 연차는 **그대로 남고**, 이름 옆에 "(비활성)"이 표시된다.
3. **반복 할 일 규칙은 중지**된다.
4. 그 사람에게 가는 **예약된 개인 알림(할 일 알림 등)은 취소**된다.
5. 그 사람이 담당자인 **예정된 배포일정**은 그대로 두고 담당자에 "(비활성)"을 표시한다. 배포 등록자에게 "담당자가 비활성화되었습니다" 알림을 보낸다. 담당자를 다시 정할 때까지 **배포 1시간 전 알림은 등록자에게** 간다.
6. 다시 활성화하면 로그인할 수 있다. 중지된 반복 할 일은 자동으로 재개하지 않는다.

## 5. 구현 메모

- 인증은 서버 세션(Spring Session). 매 요청마다 계정이 활성인지 확인한다.
- 권한 검사는 컨트롤러가 아닌 서비스 계층에서 한다.
- "본인 것만"은 엔티티의 작성자 ID와 로그인 사용자 ID 비교로 판단한다.
- 나중에 여러 팀으로 확장할 가능성은 열어두되, 지금은 `team_id` 같은 컬럼을 미리 넣지 않는다(YAGNI).
